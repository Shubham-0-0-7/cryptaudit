# cryptaudit

Static analysis for cryptographic API misuse in Rust code.

> **Status: early development.** Twenty-five rules are implemented. More are planned; see the [roadmap](#roadmap).

Modern ciphers like ChaCha20-Poly1305 and AES-GCM are sound. Real systems still break because the API is used wrongly: a reused nonce, a hardcoded key, a tag compared with `==`, a secret printed through `#[derive(Debug)]`. `cryptaudit` looks for these mistakes in your source code.

## Install and run

```sh
cargo install cryptaudit
cd your-project
cargo cryptaudit
```

Requires Rust 1.85 or newer. It parses source files only: it does not build your project or touch the network.

### Options

| Flag | Meaning |
|---|---|
| `--format human\|json\|sarif` | Output format (default `human`); `sarif` is for GitHub code scanning and other CI dashboards |
| `--min-confidence low\|medium\|high` | Hide less certain findings (default `medium`) |
| `--fail-on low\|medium\|high\|critical` | Exit with status 1 if a shown finding is at least this severe (hardening reports are listed but do not count) |
| `--fail-on-hardening` | Let hardening reports count towards `--fail-on` too |
| `--include-tests` | Also scan `tests/`, `benches/`, `examples/`, `xtask/`, `build.rs` and `#[cfg(test)]` code |
| `--config FILE` | Config file (default: `cryptaudit.toml` in the scanned directory) |
| `--no-suppress` | Ignore suppression comments and the config file |
| `--explain CA010` | Print the documentation for a rule |
| `--list-rules` | List the rules |

Exit status: `0` no findings, `1` findings, `2` the tool failed. Hardening reports (below) do not make the status `1` unless `--fail-on-hardening` is given. Files that don't parse are reported as warnings and skipped. `target/`, anything in `.gitignore`, test, fuzz and bench code (`tests/`, `benches/`, anything named like `test_utils/` or `tests_and_kats/`, and `#[cfg(test)] mod x;` files), build scripts (`build.rs`, `xtask/`) and generated files (`@generated`, `generated by`) are skipped.

## Using it in CI

`--format sarif` writes SARIF 2.1.0, the format GitHub code scanning reads, so findings show up as annotations on pull requests and in the repository's Security tab:

```yaml
# .github/workflows/cryptaudit.yml
name: cryptaudit
on: [push, pull_request]
jobs:
  scan:
    runs-on: ubuntu-latest
    permissions:
      security-events: write
      contents: read
    steps:
      - uses: actions/checkout@v4
      - run: cargo install cryptaudit
      - run: cargo cryptaudit . --format sarif > cryptaudit.sarif
        continue-on-error: true   # exit status 1 means findings, not a failure to scan
      - uses: github/codeql-action/upload-sarif@v3
        with:
          sarif_file: cryptaudit.sarif
```

Run it from the repository root with `.` so paths in the report are relative; GitHub matches them to files in the repository. Severity becomes the alert level (`critical` and `high` are errors, `medium` a warning, `low` a note) and its `security-severity` score, and the confidence is in each result's properties. To fail the build instead, use `--fail-on high` and leave out `continue-on-error`.

## Silencing a finding

If a finding is a false positive on your code, say so in the source, with a reason:

```rust
// cryptaudit:allow(CA021) compared inside a test helper, not on a secret path
assert!(mac_bytes == expected);
```

The comment goes on the flagged line or on the comment lines directly above it. List several rules with `allow(CA015, CA016)`. `// cryptaudit:allow-file(CA015) reason` silences a rule for the whole file. A directive without a reason is ignored and produces a warning, and so does one that names an unknown rule. The report counts suppressed findings, and `--no-suppress` shows them again.

For project-wide choices, add a `cryptaudit.toml` next to your `Cargo.toml`:

```toml
disable = ["CA016"]               # turn a rule off everywhere

[[allow]]
rule = "CA015"
path = "src/legacy/**"            # gitignore-style glob, relative to the scanned directory
reason = "legacy code, tracked in #42"
```

## Rules

| ID | Name | Severity | What it finds |
|---|---|---|---|
| CA010 | secret-in-debug | high | `#[derive(Debug)]` on a struct with secret fields, and hand-written `Debug`/`Display` impls that print a secret, including through a local variable |
| CA011 | copy-on-secret | medium | `#[derive(Copy)]` on a secret type: every move duplicates the key, and `ZeroizeOnDrop` becomes impossible |
| CA012 | serialize-on-secret | high | `#[derive(Serialize)]` on a type holding a secret, unless the field has `#[serde(skip)]` or custom serialisation. Always low confidence, so hidden by default: most such types exist to be serialised (4 of 22 reports were useful in two blind rounds) |
| CA013 | partialeq-on-secret | medium | `#[derive(PartialEq)]` on a newtype around a key, or a hand-written `==` on a secret type, instead of a constant-time comparison; a record that merely contains a secret is low |
| CA014 | secret-in-log | high | a secret passed to `info!`, `println!`, `panic!`, `bail!` and similar, or recorded by `#[tracing::instrument]`; reads `{}` arguments, inline `{name}` captures and tracing fields |
| CA015 | secret-not-zeroized | medium | a struct holding a secret with no `Zeroize`/`ZeroizeOnDrop`, or a buffer filled by a KDF or RNG and dropped without being wiped |
| CA016 | manual-zeroing | medium | a secret wiped with `fill(0)` or a loop, which the optimiser may delete; use `zeroize` |
| CA018 | unwrap-on-crypto-result | medium | `.unwrap()` / `.expect()` on `decrypt`, `verify_slice` and similar: tampered input panics the process |
| CA019 | verification-result-discarded | high | `let _ = mac.verify_slice(..)`, a bare `decrypt_in_place(..);`, or `.ok();`: a failed check is silently ignored |
| CA020 | assert-eq-on-mac | medium | `assert_eq!` / `assert_ne!` on a MAC or tag: not constant time, and the panic prints both values |
| CA021 | mac-compared-with-eq | high | `==` / `!=` on MAC or digest output, including a MAC stored in a local variable first, and a locally generated one-time code compared with a `token` or `code` argument; a plural `tags` is never counted, and the same generic name on both sides (`a.tag == b.tag`) is low |
| CA023 | non-csprng-for-secret | high | a key, nonce, IV or salt generated by `SmallRng`, `fastrand`, PCG, xoshiro and similar (`thread_rng` is fine) |
| CA024 | weak-primitive | high | RC4, RC2, DES and 3DES constructors (medium); MD5, MD4 and SHA-1 (low, hidden by default: most uses are checksums); low inside a library that offers the primitive (`trait Tdes`, `tdes.rs`, an `AlgorithmId::Tdes` variant) |
| CA025 | ecb-mode | high | `ecb::Encryptor`, `Cipher::aes_128_ecb()` and other ECB constructors; a name with ECB in it is low confidence |
| CA027 | hardcoded-key | high | a literal, `const` or `hex!` key or IV passed to a cipher or MAC constructor |
| CA028 | nonce-reuse | critical | the same nonce used for two encryptions, reused across loop iterations, hardcoded, derived from the clock, or filled from a cloned RNG |
| CA029 | password-compared-with-eq | high | a password or token parameter compared with `==` against a stored value, in a function named `check_user`, `verify_token`, `authenticate` and the like |
| CA062 | weak-password-hash-cost | medium | PBKDF2, bcrypt, scrypt or Argon2 with a literal work factor far below current guidance (for example PBKDF2 with 1,000 iterations, bcrypt cost 4) |
| CA063 | fast-hash-of-password | high | a value named `password` passed to SHA-2, SHA-3, MD5, BLAKE2 or BLAKE3 instead of a password-hashing function; SHA-1 is low (breach-lookup services need it), and so is a public function named after the hash (`pub fn md5_hash`) |
| CA064 | tls-certificate-validation-disabled | critical | `danger_accept_invalid_certs(true)`, `SslVerifyMode::NONE`, `ssl_verify_peer(false)`, a `ServerCertVerifier` that accepts everything; high for a literal, medium under an unrelated `if`, low when a setting about verification decides (`if config.accept_invalid_certs`): that is code offering the switch, not misusing it |
| CA065 | tls-hostname-verification-disabled | critical | `danger_accept_invalid_hostnames(true)`, `ssl_verify_host(false)`, `set_verify_hostname(false)` |
| CA066 | jwt-verification-disabled | critical | `dangerous_insecure_decode`, `insecure_disable_signature_validation()`, `validate_signature = false`, `Validation::new(header.alg)` |
| CA071 | fixed-rng-seed | critical | `seed_from_u64(42)` and similar; confident only when the output becomes a secret |
| CA072 | time-seeded-rng | critical | an RNG seeded from `SystemTime` or `Instant` |
| CA079 | fixed-cbc-iv | high | a constant IV passed to a CBC cipher |

CA010 to CA013, CA015 and CA016 are **hardening reports**: a type that derives `Debug`, a buffer that is not wiped. They matter only if something else goes wrong, and nothing in the code shows a leak happening. They are listed after the findings under their own heading, counted separately (`1 finding and 2 hardening reports in 1 file`), marked `"class": "hardening"` in JSON and SARIF, and do not change the exit status unless `--fail-on-hardening` is given. Every other rule points at code that is wrong on its own, such as a switched-off certificate check or a MAC compared with `==`.

Run `cargo cryptaudit --explain CA013` for the full description of a rule, with examples and known false positives.

Each finding has a severity (impact if exploited) and a confidence (how likely it is a true positive). Low-confidence findings are hidden by default, so the first run stays quiet. The rule list is based on a [taxonomy of Rust crypto misuse](docs/taxonomy.md); many patterns in it are specific to Rust, such as derive macros that leak secrets, `Copy` types that cannot be zeroized, and zeroing code that the optimiser removes.

**How accurate is it?** Measured, not claimed. On the last blind round (twelve crates nobody had looked at, 57 sampled reports labelled by an AI agent, not a human), the reports that point at code wrong on its own were worth acting on or fixing about 42% of the time (10 of 24), and five distinct real problems were found: a database client that accepts any TLS certificate, an HMAC compared with `!=`, passwords stored as an unsalted SHA-256, and passwords written to a trace log. The hardening reports were useful about 70% of the time (23 of 33), but almost none showed a leak happening. Treat that as one sample with wide error bars: one crate supplied 46% of the rows, the three rounds before it measured 31% on a mix of both kinds, and the noisiest rule (CA021) was right only 2 times in 10. Expect false positives; every one can be silenced with a reason (see [Silencing a finding](#silencing-a-finding)).

Evaluation on real crates, with every finding labelled true or false positive, is in [eval/triage.md](eval/triage.md). Recall on crates with known bugs (RustSec advisories) is in [eval/recall.md](eval/recall.md): 3 of 8 in-scope bugs on the first pass, 5 of 8 after two rule changes.

## How it differs from existing tools

- `cargo-audit` reports vulnerable crate versions, not misuse in your own code.
- Clippy has no cryptographic knowledge.
- CryptoGuard and CogniCrypt do this for Java only.
